# Native Ensemble Studio downloads

`EnsembleStudioServe` serves the compiled Ensemble Studio and renders requested
WAVE downloads in native FPC. The phone receives an ordinary HTTP attachment;
it does not need the browser's direct file-system picker, a secure-context
streaming save API, or a whole-song JavaScript audio buffer. There are no new
runtime dependencies beyond FPC and the operating system.

This is a dedicated, opt-in development host. `wfc_serve` remains a static-only
executable; it does not acquire rendering routes or command execution.

## Build and run

The normal `build.ps1` / `build.sh` gate builds and tests the executable in
`build/native/bin`. Append `.exe` on Windows. Stage the browser page first:

```powershell
.\build-browser-ensemble.ps1
.\build\native\bin\EnsembleStudioServe.exe --root build/browser/ensemble/www --port 4178
```

```sh
bash ./build-browser-ensemble.sh
build/native/bin/EnsembleStudioServe --root build/browser/ensemble/www --port 4178
```

The default address is `127.0.0.1`. Open `http://127.0.0.1:4178/`. For a phone
on trusted Wi-Fi, add `--bind` followed by this computer's actual private IPv4
address, and open that address with the same port. Do not start two listeners
on the same address/port. Use a different port to try the dedicated host while
an existing static instance is still running.

The [LAN/firewall rules](development-tools.md#access-from-a-trusted-local-network)
apply here too. A program-specific firewall rule must name
`EnsembleStudioServe`, not the different `wfc_serve` executable. Do not disable
the firewall or forward this port from the Internet.

A focused FPC build, after creating the output directories, is:

```text
fpc -B -Mdelphi -Fusrc -Futools -Fuexamples/music/06_EnsembleStudio -FUbuild/ensemble/http/units -FEbuild/ensemble/http/bin examples/music/06_EnsembleStudio/EnsembleStudioServe.lpr
```

The host accepts `--root DIRECTORY`, optional `--port PORT`, `--bind ADDRESS`,
and positive `--max-requests N` for process tests. `--help` and `--version`
work alone. Stop the foreground host with Ctrl+C.

## On the phone

1. Select **Developed phrases** and the seed at the top of the page.
2. In **Continuous Stream**, enter your own **Requested seconds** and desired
   working-segment/search settings.
3. Follow **Download WAVE from FPC server** once capability discovery succeeds.
4. Use your browser's download manager to inspect progress, completion, errors,
   or cancellation.

The link opens a separate browsing context, preserving the studio page. A
click means only that a download was requested; the page never labels it
completed. The page's **Cancel pending stream** button controls browser-side
Save As operations, not this independent native download. Editing settings
changes the next download link; it cannot recall a request already handed to
the browser.

This creates a fresh composition from the captured continuous-stream inputs.
The finite editor's Bars, locks, repair scope, and New session operation are
not transferred. To match an unlocked developed finite score, use the same
seed/profile and total extent: at this demo's fixed tempo, each bar is two
seconds. The original structural profile is still available but adding time
does not supply its missing musical development.

There is no arbitrary minute ceiling. Decimal seconds are preserved and
rounded upward to the next quarter-second musical cell. Exact numeric and
RIFF/RF64 capacities, generation cost, destination space, and connection
reliability remain real limits. Request targets share the development
server's 2,048-byte envelope, including the decimal spelling and options;
that is a protocol-size bound, not a composition-duration target.

The finite **Build full-score WAV** action remains a separate in-memory
preview adapter with its existing 60-second bound. It never clips a longer
score. This native download path and direct browser streaming do not inherit
that preview policy.

## Transport and failure contract

The server retains the existing bounded frame/PCM source plus one HTTP tail
byte. It creates no output file, temporary song, external process, or growing
audio timeline. It sends the exact preflight `Content-Length` and an
attachment filename containing the seed, profile, and actual tick count.
WAVE bytes are generated by the same project-owned renderer as the native
command-line stream.

The first PCM block is generated before success headers. An initial generation
failure returns a plain-text error response. After headers, a generation,
validation, or transport failure closes the connection without padding the
body or claiming success. The last body byte is withheld until the source's
exact frame count and WAVE finalization succeed. A short body is an incomplete
HTTP message, not a completed file ([HTTP/1.1 section 8](https://www.rfc-editor.org/rfc/rfc9112.html#section-8)).
The browser controls how it reports that failure and whether it retains a
partial download; the server does not atomically publish a destination file.

Each bounded socket write has a send deadline; the whole composition has no
15-second render deadline. A disconnect is observed at a write boundary, not
an interrupt inside a synchronous phrase/segment solve. There is no Range
support or resume checkpoint: a fresh request regenerates from the beginning.

The host is sequential. One active download can delay other requests,
including page assets and capability discovery. If discovery times out while
the host is busy, wait for the download to finish and reload. This is not a
multi-user rendering farm, background job queue, or persistent artifact store.

## Narrow request surface

The optional same-origin capability endpoint is `/ensemble-stream-v1`.
It returns exactly version 1, the fixed `/ensemble-wave-v1` path, and a
128-bit OS-random capability token. The browser accepts only a bounded ASCII
response with those three fields; it never follows a returned arbitrary URL,
redirect, or remote origin. Static hosting can return 404 without breaking
existing Save As, short previews, MIDI, or native command-line fallback.

The WAVE endpoint accepts GET/HEAD and exactly eight query fields: token,
seconds, seed, profile, segment-cells, backtracks, pass-backtracks, and trace.
Unknown/duplicate/missing fields and encoded aliases are rejected. The seed is
an unsigned 32-bit decimal; trace is exactly 0 or 1. HEAD validates and describes
the requested output without constructing a graph or generating audio.

A missing or incorrect capability receives 403. Invalid settings with a valid
capability receive 400. There are no output-path parameters, uploads, script
execution, arbitrary commands, CORS grants, or directory listings. Static
files retain the shared server's path/handle containment checks. Responses
are non-cacheable, content-sniffing is disabled, and dynamic resources declare
same-origin resource policy ([Fetch Standard](https://fetch.spec.whatwg.org/#cross-origin-resource-policy-header)).

The capability prevents a blind cross-site request from guessing a rendering
URL. It is not authentication or TLS: anyone who can read this trusted-LAN
server can obtain it. It changes when the process restarts and is never
printed in server diagnostics. A download URL contains it and may appear in
browser history; do not share that URL. Serve only an owned, trusted staged
site. Do not expose the host to untrusted networks.

## Verification scope

`wfc_ensemble_http_test` checks the same strict protocol and duration/filename
planning on native FPC and pas2js, including RF64 planning without enormous
audio allocation. `wfc_serve_test` checks response state, bounded blocks,
header injection rejection, the withheld completion byte, HEAD, and transport
failure, alongside the existing real static-server checks.

`wfc_ensemble_http_process_test` starts the actual native host, exercises
capabilities and rejection paths, compares a complete download longer than
the preview bound against independently pulled native PCM, and checks
disconnect recovery. Browser fixtures exercise discovery, stale inputs,
bounded/malformed responses, release, and handoff without pretending a
navigation is a completed download. These are protocol/runtime checks, not
a claim that every mobile browser or Wi-Fi configuration has been tested.
